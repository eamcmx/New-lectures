What this lecture covers

This lecture introduces the core ideas of functional programming (FP): building software out of functions over immutable variables. We move from a knowledge recap of expressions vs. statements into the theoretical foundation of lambda calculus, and then through the main FP concepts — pure functions, parallelization, memoization, laziness, recursion, referential transparency, immutability, and higher-order functions.

We close with the practical trade-offs (advantages and disadvantages) of the pure-functional style and a short group activity to put the ideas into practice.

The goal isn't to pick a tribe — OOP or FP — it's to use functions to the best effect for clean, maintainable software.

One-line definition

Functional programming is all about building functions for immutable variables, using functions to the best effect for creating clean and maintainable software.

1

Expressions vs. Statements

An expression is a combination of values and functions that the compiler combines and interprets to produce a new value. A statement is a standalone unit of execution that doesn't return anything.

The useful way to think about it: the purpose of an expression is to create a value (possibly with some side-effects), while the sole purpose of a statement is to have side-effects. Functional programming leans heavily on expressions, because an expression evaluates to a value rather than mutating state.

If it produces a value, it's an expression. If its whole point is to do something on the side, it's a statement.

Why it matters for FP

FP prefers expressions because evaluating an expression yields a value without needing to assign and mutate variables.

if/then/else as a statement (imperative)
let result;
if (x > 0) {
  result = "positive";
} else {
  result = "non-positive";
}
// the if-block returns nothing; it only assigns `result`
if/then/else as an expression (functional)
const result = x > 0 ? "positive" : "non-positive";
// the whole construct evaluates to a value

InteractiveNow you choose how to write the same branching logic and watch what comes out the other end. One form evaluates to a value you can bind; the others run purely to assign or print. Decide which one fits the functional style and see why.

2

Lambda Calculus

Lambda calculus is a theoretical framework that describes functions and their evaluation. Instead of statements, it makes use of expressions: unlike a statement, which is executed to assign variables, the evaluation of an expression produces a value.

Developed by Alonzo Church, lambda calculus forms the basis of almost all functional programming languages in use today. It is similar in spirit to the Turing machine that laid the foundation for the imperative style — and remarkably, it can be seen as the most succinct programming language of them all: anything computable can be expressed in it.

In the lecture's notation we write the identity function as $\lambda x.\, x$ — given any input it returns that input unchanged. Applying an "add one" function to 5, written $(\lambda x.\, x + 1)\, 5$, evaluates to 6. Here $x$ is the bound variable, the body after the dot is the result, and juxtaposition denotes application:

$$(\lambda x.\, x + 1)\, 5 \;=\; 6.$$

Lambda calculus is to functional programming what the Turing machine is to imperative programming — the foundation underneath the whole style.

Three things to remember

It describes functions and their evaluation; it is computationally complete (anything computable is computable in it); and it underpins nearly every functional language.

identity and a simple function in lambda notation
λx. x          -- the identity function
(λx. x + 1) 5  -- apply 'add one' to 5, evaluates to 6

InteractiveNow you feed in a lambda term and step through it: we find the redex, substitute the argument for the bound variable, and reduce until no more applications remain. You'll see for yourself that evaluating an expression produces a value — the whole point Church built the calculus around.

3

Pure Functions

A pure function is a function whose return value is determined only by its input values, without observable side effects. Pure functions have two important properties:

  • They always produce the same output for the same arguments, regardless of any other factors (this is tied to immutability).
  • They are deterministic and have no side-effects — they don't modify their arguments or global variables.

Because of this, programs built in the functional paradigm are easy to debug, and pure functions make writing concurrent applications easier.

Same inputs, same output, no surprises — that's the whole promise of purity.

Pays off in concurrency

Because pure functions never touch shared state, they make concurrent applications easier to write and reason about.

pure vs. impure
// pure: output depends only on inputs, no side effects
function add(a, b) {
  return a + b;
}

// impure: reads/writes external state
let total = 0;
function addToTotal(x) {
  total += x;      // side effect
  return total;    // depends on hidden state
}
4

What purity buys: parallelization, memoization, laziness

Purity isn't just tidiness — it unlocks concrete optimizations.

Parallelization. Pure functions can always be parallelized. In the slide example, a sequential #map took 10 seconds while the parallel #pmap version took only 2.5 seconds — but we can only swap #map for #pmap if we know the function called is pure.

Memoization. Because pure functions are referentially transparent, we only need to compute their output once for given inputs. Caching and reusing that result is called memoization, and it can only be done safely with pure functions.

Laziness. Invoking a pure function specifies a dependency: this output depends on these inputs. But if you never use the output, and the function can't cause side effects, it doesn't matter whether it's called at all — so a smart system can be lazy and optimize the call away. With lazy evaluation, only the values actually needed are computed; the rest is ignored.

When the code is written in a functional style, a capable compiler can memoize results, parallelize instructions, and wait before evaluating — all because it can trust your functions.

The catch

Every one of these optimizations depends on purity. Swap in parallel or cached evaluation for an impure function and you'll get wrong, non-deterministic results.

parallel map only when the function is pure
results = map  pureFn collection   -- ~10s, sequential
results = pmap pureFn collection   -- ~2.5s, parallel (safe: pureFn is pure)
5

Recursion instead of loops

Functional programming languages have no for or while loops. Instead, they rely on recursion for iteration.

Recursion is implemented using recursive functions, which repetitively call themselves until a base case is reached. The base case stops the recursion; every recursive call should make progress toward it. The standard recursive definition of factorial captures the shape exactly — $n! = n \times (n-1)!$ for $n > 0$, with base case $0! = 1$.

No loop counters to mutate — just a function that calls itself with a smaller problem until it bottoms out.

Mind the base case

Without a reachable base case, a recursive function never terminates. Each call must move closer to that stopping condition.

factorial by recursion (no loops)
function factorial(n) {
  if (n === 0) return 1;     // base case
  return n * factorial(n - 1); // recursive case
}

InteractiveNow you pick an n and watch factorial(n) recurse: each call pushes a frame that waits, the base case stops the descent, and the answers multiply back up as the stack unwinds. This is iteration without a single mutable loop counter.

6

Referential transparency & immutability

Referential transparency means a variable, once defined, isn't allowed to change the value it holds throughout the program's execution. It assures that the same language expression always gives the same output — and because of this, any variable can be safely replaced by its actual value at any point in the program.

Functional programs have no assignment statements. To store additional values you must define new variables rather than reassign existing ones, so the state of a variable is constant at any moment in time. This is the same idea as immutability: once a variable is initialized it cannot be modified; you can only create a new variable. The immutable nature of variables preserves the state throughout the program's execution and eliminates undesired effects.

If the same expression always means the same value, you can reason about — and rewrite — your program with the confidence of algebra.

Substitution model

Referential transparency lets you replace any expression with its value (and vice versa) without changing the program's meaning.

create a new value, never mutate
const xs = [1, 2, 3];
const ys = [...xs, 4]; // new array; xs is untouched
// xs === [1,2,3], ys === [1,2,3,4]
7

First-class & higher-order functions

In the functional style, functions are treated as values — they are first-class functions. This means they can be passed to other functions as parameters, returned from functions, or stored in data structures, just like any ordinary value.

A higher-order function is a function that takes other functions as arguments and/or returns functions. First-class functions are what make higher-order functions possible in functional programming languages.

Once functions are just values, you can build functions that build functions — composition becomes the main tool.

First-class ⇒ higher-order

Because functions are first-class values, you can write higher-order functions like map, filter, and reduce that take a function as input.

a higher-order function that takes a function
const map = (fn, xs) => xs.map(fn);
const double = x => x * 2;
map(double, [1, 2, 3]); // [2, 4, 6]
8

Advantages & disadvantages of pure functions

Advantages. Because pure functions don't change any state and depend entirely on their input, they are simple to understand — their return value is their output, and their signature tells you the argument and return types. Avoiding changes to outside data makes concurrency efficacious. Purity supports lazy evaluation (compute and store a value only when required), produces no hidden output (making debugging and testing easier), and treating functions as values that can be passed around enhances code readability.

Disadvantages. Immutable values combined with recursion might reduce performance. In some cases writing pure functions reduces code readability. Although writing pure functions is easy, combining them with the rest of the application and with I/O operations is hard. And writing programs recursively, in place of loops, can be a daunting task.

Purity is a trade: you gain reasoning power, testability, and concurrency, but you pay in performance and in the friction of dealing with the messy, side-effecting real world.

Strengths

Easy to understand and test, no hidden output, friendly to concurrency, supports lazy evaluation, and improves readability via functions-as-values.

Costs

Immutability plus recursion can hurt performance; integrating pure code with I/O is hard; recursive style can be harder to write than loops.

Self-checkNow you test yourself on the payoff of purity: four questions on why pure functions can be parallelized, memoized, and evaluated lazily — and what referential transparency actually licenses you to do.

Practice — try these on your own

Small activities to test your grip on today's ideas. Try each one first, then reveal the worked solution to compare. Nothing here is handed in — it's purely for your own checking.

1 · Classify expressions vs. statements

For each fragment below, decide whether it is an expression (produces a value) or a statement (executed for its side-effect, returns nothing). Justify each answer in one phrase.

fragments to classify
(a) 3 + 4 * 2
(b) let y = 10;
(c) x > 0 ? "pos" : "neg"
(d) console.log("hi");
(e) Math.max(a, b)
Self-check after you've tried
  • Each item is labelled either 'expression' or 'statement'.
  • Ask yourself 'does this evaluate to a value I could assign to a variable?' — if yes, it's an expression.
  • A fragment whose only job is a side-effect (assignment, printing) is a statement.
Show worked solution

Recall the rule: an expression combines values and functions to produce a new value; a statement is a standalone unit of execution whose purpose is a side-effect and which returns nothing.

  • (a) 3 + 4 * 2 → expression. It evaluates to the value 11.
  • (b) let y = 10; → statement. Its purpose is the side-effect of binding y; the declaration itself returns nothing.
  • (c) x > 0 ? "pos" : "neg" → expression. The ternary evaluates to one of the two string values, so it can be assigned.
  • (d) console.log("hi"); → statement. Its whole point is the side-effect of printing; it yields no useful value.
  • (e) Math.max(a, b) → expression. A function application that produces a value (the larger of a and b).

Result: expressions are (a), (c), (e); statements are (b), (d). The discriminating question is always "does evaluating this produce a value?"

2 · Spot the impurity and fix it

The function below is not pure. Identify why it violates purity, then rewrite it so that its return value depends only on its inputs and it causes no observable side effects.

impure function
let count = 0;
function tag(label) {
  count += 1;
  return label + "-" + count;
}
Self-check after you've tried
  • You named at least one side-effect (mutating count) and the hidden-state dependency.
  • Your rewritten function returns the same output for the same arguments.
  • The rewrite touches no variable declared outside it.
Show worked solution

Why it's impure. A pure function's return value must be determined only by its inputs, with no observable side effects. tag breaks this on two counts:

  • It mutates external state (count += 1) — a side effect.
  • Its output depends on hidden state: calling tag("a") twice gives "a-1" then "a-2". Same input, different output ⇒ not deterministic, not referentially transparent.

Fix. Make the counter an explicit input and return the next value alongside the result, so nothing outside the function changes:

pure rewrite
function tag(label, count) {
  return { value: label + "-" + (count + 1), count: count + 1 };
}

Now tag("a", 0) always yields { value: "a-1", count: 1 }. The caller threads the new count forward instead of relying on a mutable global. Result: same inputs ⇒ same output, no external mutation — the function is pure and could be safely memoized or parallelized.

3 · Turn a loop into recursion

Functional languages replace for/while loops with recursion. Rewrite this imperative sum as a recursive function with an explicit base case, and state what the base case is and how each call makes progress toward it.

imperative sum
function sum(xs) {
  let total = 0;
  for (const x of xs) total += x;
  return total;
}
Self-check after you've tried
  • Your function has a clearly identified base case (empty list → 0).
  • Each recursive call is made on a strictly smaller input.
  • No mutable accumulator variable is reassigned.
  • sum([1,2,3]) returns 6.
Show worked solution

Iteration in FP is expressed by a function that calls itself until a base case stops it. For summing a list:

  • Base case: an empty list sums to 0.
  • Recursive case: the sum of a non-empty list is its first element plus the sum of the rest.
  • Progress: each call drops the head, so the list shrinks toward the empty base case and the recursion terminates.
recursive sum
function sum(xs) {
  if (xs.length === 0) return 0;        // base case
  const [head, ...tail] = xs;           // split off the first element
  return head + sum(tail);              // recursive case
}

Tracing sum([1, 2, 3]):

$$\text{sum}([1,2,3]) = 1 + \text{sum}([2,3]) = 1 + (2 + \text{sum}([3])) = 1 + (2 + (3 + \text{sum}([\,]))) = 1 + 2 + 3 + 0 = 6.$$

Result: 6, with no mutable accumulator — only function application and the base case to terminate.

4 · Write a higher-order function

Functions are first-class values, so they can be passed as arguments. Write a higher-order function applyTwice(fn, x) that returns the result of applying fn to x, and then to that result again — i.e. fn(fn(x)). Then evaluate applyTwice(n => n + 3, 10) by hand.

Self-check after you've tried
  • applyTwice takes a function as its first argument.
  • It applies that function exactly twice, feeding the first result into the second call.
  • Your hand evaluation of applyTwice(n => n + 3, 10) gives 16.
Show worked solution

A higher-order function takes another function as an argument and/or returns one. Here applyTwice takes the function fn as a first-class value and applies it twice:

applyTwice
function applyTwice(fn, x) {
  return fn(fn(x));
}

Hand evaluation of applyTwice(n => n + 3, 10). Let fn = n => n + 3.

  • Inner call: fn(10) = 10 + 3 = 13.
  • Outer call: fn(13) = 13 + 3 = 16.

So applyTwice(n => n + 3, 10) evaluates to 16. Because fn here is pure, applyTwice is itself pure: the same fn and x will always yield the same answer.
