Mobile-frame rotations & inverting a homogeneous transform

Why a real robot doesn't rotate the way your matrix says — and how to derive $T^{-1}$ by inspection.

Lecturer · opening
Last class we built the matrices that translate and rotate a mobile frame relative to a fixed one. Today we hit a wall: ask the robot to rotate around the fixed $z$-axis and it doesn't swing around the base — it spins in place around an axis through its tool. So today is a thinking class. We'll figure out, together, what matrix mimics what the robot actually does, and then we'll flip the whole question around and invert a homogeneous transform — by inspection, then by formula.

§ 0

What this lecture covers

Two things. First: the rotation matrices we built last class describe motion around the fixed frame's axes — but real robots, when you tell them "rotate around $z$," rotate around an axis parallel to fixed $z$ that passes through the mobile frame's origin. We need a tool that mimics that.

Second: given a transform $T^0_3$ that expresses frame 3 in frame 0, how do we write $T^3_0$ — the same physical relationship but with the reference flipped? We'll derive it by visual inspection, notice that the rotation block is just the transpose, and end with the closed-form inverse of a homogeneous transformation matrix.

If today feels more like a puzzle than a lecture, that's deliberate — the point is the thinking, not the formula.
Today's two deliverables

What you'll walk out with

A function that rotates around the mobile-frame axes (for $x$, $y$, and $z$), and a function inverseT(M) that returns the inverse of a homogeneous transformation matrix.

§ 1

Where we left off — translating and rotating in two frames

We've been driving a mobile coordinate system with respect to a fixed base. Translations along $x$, $y$, $z$ work cleanly in either frame — you move along the line you point at. Rotations around the mobile axes also behave the way the matrices predict: rotate around mobile $x$, the frame tips forward; rotate around mobile $y$, it yaws; rotate around mobile $z$, it spins about its own vertical.

So for everything we've built so far, the matrix and the geometry agree. Before we break that agreement in the next section, let's spend a moment with the case where it holds.

Mental model

Where each rotation pivots

Mobile-axis rotations follow the frame. Fixed-axis rotations should pivot around the world origin — that's the part we're about to test.

Pick a mobile axis and rotate. Watch the attached frame tip, yaw, or spin — and notice the rotation axis stays welded to the frame, not to the world.

§ 2

The discrepancy — what the real robot actually does

Now we ask the robot: rotate around the fixed $z$-axis. By the math we built last class, the tool should swing in a big arc around the base — the matrix $R_z(\theta)$ pivots every point about the world origin. It doesn't. The tool spins in place.

Look closely and you can see what's happening. The robot is rotating around an axis that is parallel to fixed $z$, but passing through the origin of the mobile frame (the tool). Same story for $x$ and $y$ — the rotation axes are parallels of the world axes, anchored at the tool, not at the base.

So the matrix "rotate around world $z$" and the robot command "rotate around $z$" are not the same operation. We need a matrix that mimics the robot's behaviour.

The matrix says one thing, the robot does another — and the robot is not wrong. Our job is to describe what the robot actually does.
The gap

Same direction, different pivot

Fixed-frame rotation matrix → pivots about the world origin. Robot "rotate around $z$" → pivots about an axis parallel to world $z$, through the tool's current position.

Side by side: the left tool obeys the fixed-axis rotation matrix and swings around the base; the right tool does what the robot does and spins in place about a parallel axis. Step through the frames and convince yourself they really are different operations.

§ 3

Today's exercise — derive the matrix that mimics the robot

The thinking task: assemble the transforms you already have to reproduce the robot's behaviour. The recipe we sketched on the board:

  1. Start at the fixed frame at the base.
  2. Translate along $x$ to get the mobile frame out to the tool's position.
  3. Elevate (translate in $z$) to lift the mobile frame up.
  4. Rotate the mobile frame 45° around one of its own axes, then 45° around another, to orient it like the tool.
  5. Now perform the rotation — around one of the resulting mobile axes (which is parallel to world $x$, $y$, or $z$, but anchored at the tool).

The key insight: position the mobile frame first, then rotate. The robot doesn't need a carobka (linear carriage) to do this — the chain of transforms does it for you.

Position first, then rotate. That ordering is the whole trick.
Why this works

The geometric punchline

Once the mobile frame sits at the tool with the correct orientation, a rotation expressed in that mobile frame is exactly the rotation the robot performs — a spin around an axis through the tool, parallel to the requested world axis. Two things that look different (mobile-axis rotation vs. parallel-to-fixed-axis-through-tool rotation) become the same once the mobile frame has been placed.

Mechanically, the composition order matters: you apply the new rotation on the right of the current transform.

$$T_\text{new} \;=\; T_\text{current}\cdot R_\text{axis}(\theta)$$

Left-multiplication would rotate with respect to the fixed frame. Right-multiplication rotates with respect to the mobile frame — which is exactly what we want.

shape of the function you're writing
rotateAroundMobileX(T_current, angle)
  # 1. start from the current mobile frame T_current
  # 2. build R_x(angle) as a 4x4 homogeneous transform
  # 3. compose on the right:  T_new = T_current @ R_x
  # 4. return the new transform

# then the same for y and z

Drag the five transforms into order to mimic the robot's behaviour. Rotate before you translate and the rotation pivots about the base — wrong. Get the ordering right and the mobile frame ends up at the tool, oriented like the tool, and the final rotation happens about an axis through the tool parallel to a world axis.

§ 4

Changing the reference frame — from $T^0_3$ to $T^3_0$

On to the second problem. We have the transform that expresses frame 3 in frame 0:

$$T^0_3 \;=\; \begin{bmatrix} 0 & 1 & 0 & 5 \\ 0 & 0 & -1 & 4 \\ -1 & 0 & 0 & 3 \\ 0 & 0 & 0 & 1 \end{bmatrix}$$

We want the opposite — frame 0 expressed in frame 3, i.e. $T^3_0$. Same physical setup, the boxes haven't moved, but the reference is now frame 3 instead of frame 0. The lecturer treats "inverting $T$" and "changing the frame of reference" as the same operation — they describe the same geometry from opposite sides.

What changes

Read the columns differently

The columns of the rotation block now describe how the fixed axes $x_0, y_0, z_0$ look from the mobile viewpoint — and the translation describes where the world origin sits relative to the tool. The matrix is built the same way; what changes is who is doing the looking.

§ 5

Read $T^3_0$ off the axes by visual inspection

Don't compute anything yet — just look at the axes. For each fixed-frame axis, ask: which mobile-frame axis does it lie along, and with what sign? That triple is the column of the new rotation block.

  • $x_0$ from frame 3: parallel to $y_3$. So the first column of the rotation block is $(0,\,1,\,0)^T$.
  • $y_0$ from frame 3: parallel to $-z_3$. Column 2 is $(0,\,0,\,-1)^T$.
  • $z_0$ from frame 3: parallel to $-x_3$. Column 3 is $(-1,\,0,\,0)^T$.

So the rotation block of $T^3_0$ is

$$R^T \;=\; \begin{bmatrix} 0 & 0 & -1 \\ 1 & 0 & 0 \\ 0 & -1 & 0 \end{bmatrix}$$

Compare that to the rotation block of $T^0_3$. It's the transpose. Rows became columns; the orientation part of the inverse is just $R^T$.

This is the moment to notice that inverting a rotation matrix is free — no determinant, no cofactors, just flip it across the diagonal.
Identity

Rotation block of $T^{-1}$

For any rotation matrix $R$ (orthonormal columns), $R^{-1} = R^T$. The columns of $R$ are mutually orthonormal unit vectors, so $R^T R = I$ by definition — the diagonals are dot products of unit vectors with themselves ($=1$), the off-diagonals are dot products of perpendicular vectors ($=0$). So the rotation part of the inverse transform is the transpose of the rotation part of the original.

transpose, by example
A =  | 1 2 3 |          A^T = | 1 4 7 |
     | 4 5 6 |                | 2 5 8 |
     | 7 8 9 |                | 3 6 9 |

Step through reading each column of the inverse rotation block by inspection: where does $x_0$ point from frame 3, then $y_0$, then $z_0$. After the third column lands, the original $R$ from $T^0_3$ overlays and each of its rows snaps onto the corresponding column — and the transpose appears.

§ 6

What about the translation column?

The translation column is not just copied over, and it's not just $-p$ either. Work it out by multiplying the transposed rotation by the original position vector $p = (u,v,w)^T = (5,4,3)^T$, then negating the result:

  • Row 1 of $R^T$ times $p$:   $0\cdot5 + 0\cdot4 + (-1)\cdot3 = -3$
  • Row 2:   $1\cdot5 + 0\cdot4 + 0\cdot3 = 5$
  • Row 3:   $0\cdot5 + (-1)\cdot4 + 0\cdot3 = -4$

So $R^T p = (-3,\,5,\,-4)^T$. Multiply the whole result by $-1$ and you get the translation column of $T^3_0$:

$$-R^T p \;=\; (3,\,-5,\,4)^T$$

That is the new translation. Two transformations packed into one expression: negating $p$ flips the direction (base-to-tool becomes tool-to-base); multiplying by $R^T$ re-expresses the flipped vector in the new frame's coordinates. Skip either step and the inverse is wrong.

Sign matters

Not cosmetic

The minus sign is the difference between "where is the tool from the base" and "where is the base from the tool." Opposite vectors, expressed in different frames. Drop the minus and $T^{-1} T \ne I$.

§ 7

The closed form for the inverse

Putting both pieces together, the inverse of a homogeneous transformation matrix is:

$$T^{-1} \;=\; \begin{bmatrix} R^T & -R^T p \\ 0\;\;0\;\;0 & 1 \end{bmatrix}$$

where $R$ is the $3\times 3$ rotation block and $p = (u,v,w)^T$ is the translation column of the original $T$. The bottom row stays $[0\;0\;0\;1]$. This is changing the frame of reference — same geometry, observed from the other side.

One transpose, one matrix–vector product, one sign flip. Cheaper than a general $4\times 4$ inverse, and exact — as long as $R$ stays orthonormal.
Why this beats inv(T)

Cheap and clean

A general $4\times 4$ inverse costs $\sim 64$ multiplications and can lose precision. The homogeneous shortcut is one transpose (free), a $3\times 3$ matrix–vector product ($\sim 9$ mults), and three sign flips — and it is exact, not an approximation, as long as $R$ has stayed orthonormal.

the result for our worked example
T^0_3 =  | 0  1  0   5 |        T^3_0 =  | 0  0 -1   3 |
         | 0  0 -1   4 |                 | 1  0  0  -5 |
         |-1  0  0   3 |                 | 0 -1  0   4 |
         | 0  0  0   1 |                 | 0  0  0   1 |

Verify by computing $T^3_0 \cdot T^0_3$ — it must be the $4\times 4$ identity. If your result has a wrong sign anywhere, almost always the culprit is the translation column: either the minus was dropped, or $R$ wasn't transposed before multiplying.

Four quick questions to catch the mistakes people actually make: transposing the wrong block, forgetting the minus, mixing up $-R^T p$ and $-R p^T$, and reaching for np.linalg.inv when the shortcut is right there.

§ 8

Code the inverseT function

Now turn the formula into a function. Signature: inverseT(T) takes a $4\times 4$ homogeneous transform and returns its inverse using the shortcut — not a generic matrix inversion routine. The function should:

  1. Slice out the $3\times 3$ rotation block $R$ and the $3\times 1$ translation column $p$.
  2. Transpose $R$.
  3. Compute $-R^T p$.
  4. Reassemble the $4\times 4$ with $R^T$ in the top-left, $-R^T p$ as the translation column, and $[0\;0\;0\;1]$ as the last row.

Test it: inverseT(T) @ T must equal the identity to numerical precision.

Sanity check

When the test fails

If $T^{-1} T \ne I$, you almost certainly (a) forgot the minus sign on the translation, (b) transposed the whole $4\times 4$ instead of just the $3\times 3$ rotation block, or (c) dropped the bottom row. In that order of likelihood.

skeleton — fill in for your language of choice
def inverseT(T):
    R = T[0:3, 0:3]
    p = T[0:3, 3]
    Rt = R.T
    t  = -Rt @ p
    Tinv = np.eye(4)
    Tinv[0:3, 0:3] = Rt
    Tinv[0:3, 3]   = t
    return Tinv

Write the function in the editor, run it against the lecture's $T^0_3$, and the harness checks both that you matched the by-inspection $T^3_0$ and that $T^{-1}\cdot T$ comes out to the identity within $10^{-9}$. Calling a generic matrix-inverse routine fails the check — the shortcut is the point.
