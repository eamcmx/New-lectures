Last class we got a single point to ride along with a rotating frame — today we make it dance. We'll plot that point in three dimensions with MATLAB, watch a tiny "fly" trace the motion as the mobile frame spins, and then stack three rotations one after another. By the end you'll derive the compound rotation matrix $R_c = R_z(\theta_3)\,R_y(\theta_2)\,R_x(\theta_1)$ by hand and prove that MATLAB gives you exactly the same thing.
§ 00

What this lecture covers

We pick up the exercise from last class — a point $a_{uvw}$ pinned inside a mobile frame — and finally see it. First we'll plot the fixed frame, the rotated frame, and the point all together in MATLAB. Then we'll loop the rotation angle so the whole scene animates.

From there we step up to three sequential rotations: spin around $x$, then $y$, then $z$. We'll build the resulting compound rotation matrix two ways — the slow, satisfying hand multiplication, and a rotacomp(t1,t2,t3) function — and verify that both give the same answer.

The through-line: every motion of a rigid body in space reduces to multiplying these $3\times 3$ matrices in the right order.

Yes, we could let MATLAB do all of it — but this is university. You need to remember how it works from the beginning.
Pre-req

You should be comfortable with the elementary rotation matrices $R_x(\theta)$, $R_y(\theta)$, $R_z(\theta)$ from last class, and with multiplying $3\times 3$ matrices by hand.

Tools today

MATLAB's plot3, view, hold on, plus our own drawSyst(), rota_x/y/z() helpers, and a brand-new rotacomp() we'll write together.

§ 01

Recap — the point that rides the frame

From last class: we have a point $a_{uvw} = (0.3,\ 0.4,\ 0.5)$ expressed in the mobile frame $\{u,v,w\}$. Initially the mobile frame is perfectly aligned with the fixed frame $\{x,y,z\}$, so the relationship between them is the identity matrix.

When we rotate the mobile frame by $\theta$ around $x$, the point's coordinates in the mobile frame don't change — the point is glued to that frame. What changes is its description in the fixed frame:

$$a_{xyz} = R_x(\theta) \cdot a_{uvw}$$

That's the entire move. Every animation today is just this formula evaluated over and over.

The point doesn't move relative to the frame it lives in — the frame moves, and we re-describe the point in the other frame's language.
Why identity?

When two frames share origin and axes, the rotation between them is $I_{3\times 3}$. Any subsequent motion is pre-multiplied onto that identity.

The point in mobile coordinates (column vector!)matlab
a_uvw = [0.3; 0.4; 0.5];   % NOTE the semicolons — column, not row
Re-describe it in the fixed frame after a rotationmatlab
R    = rota_x(-30);          % rotation matrix
a_xyz = R * a_uvw;           % 3x3  *  3x1  ->  3x1

WidgetDrag $\theta$ and watch the same physical point ($a_{uvw}$ fixed in the mobile frame) get re-described as the mobile frame spins. The fixed-frame coordinates $a_{xyz}$ update live underneath.

§ 02

Plotting the scene in 3-D

MATLAB makes 3-D plotting almost embarrassingly easy. We draw the fixed frame with our helper drawSyst(E), freeze the figure with hold on, and drop the point in with plot3.

Use help plot3 if you ever forget the syntax — the signature is plot3(X, Y, Z, ...) with the usual marker/colour options. The view(...) command sets the camera angle so the scene is readable.

Don't forget hold on

Without hold on, each new plot3 clears the previous one and you'll think your code is broken.

Draw the fixed frame and a single pointmatlab
E = eye(3);              % fixed frame = identity
drawSyst(E);             % our helper draws the xyz arrows
hold on
plot3(0.3, 0.4, 0.5, '.', 'MarkerSize', 20);
§ 03

Example 4 — animate the point around one axis

Now we let $\theta$ sweep from $0°$ to $270°$ in a for loop. Inside the loop we recompute the rotation matrix, recompute $a_{xyz}$, clear the figure, redraw both frames, and replot the point at its new coordinates.

The key trick: when you call plot3, you must index into the result vector — a_xyz(1,1), a_xyz(2,1), a_xyz(3,1) — not hard-code 0.3, 0.4, 0.5. That's how the dot rides along with the moving frame.

That little fly is just our point — but watching it sweep is when the maths suddenly clicks.
Result

A "fly" that traces an arc through 3-D space, with the mobile frame's axes rotating beneath it and the rotation matrix updating live in the workspace.

Animated rotation around z (Example 4)matlab
a_uvw = [0.3; 0.4; 0.5];
E     = eye(3);

for t = 0:0.5:270
    clf
    hold on

    R     = rota_z(t);
    a_xyz = R * a_uvw;

    drawSyst(E);                 % fixed frame
    drawSyst(R);                 % mobile frame after rotation
    plot3(a_xyz(1,1), a_xyz(2,1), a_xyz(3,1), ...
          '.', 'MarkerSize', 20);

    drawnow
end
§ 04

Debug aside — row vs column vector

A student hit Error using * Incorrect dimensions for matrix multiplication. The cause: writing a_uvw = [0.3, 0.4, 0.5] with commas produces a $1\times 3$ row vector. You can't multiply a $3\times 3$ matrix by a $1\times 3$ row — the inner dimensions don't agree.

Fix: use semicolons to make it a $3\times 1$ column. Double-click the variable in the Workspace panel to confirm the shape.

The fix

[0.3; 0.4; 0.5] ✓ (column, $3\times 1$) vs [0.3, 0.4, 0.5] ✗ (row, $1\times 3$).

§ 05

Stacking three rotations

Now the real question: what if we rotate around $x$ then $y$ then $z$, one after the other? Each rotation is applied to the result of the previous one.

In robotics we read the multiplication right-to-left — the rightmost matrix acts first. Starting from identity:

$$R_c \;=\; R_z(\theta_3)\; R_y(\theta_2)\; R_x(\theta_1)\; I$$

Multiplying anything by $I$ gives the same thing back, so the first step just collapses to $R_x(\theta_1)$. From there we pre-multiply by $R_y(\theta_2)$, then by $R_z(\theta_3)$, accumulating the compound matrix.

This sequence of motions — first $x$, then $y$, then $z$ — is exactly what we'd ask a real robot wrist to do.
Convention check

Each $\theta_i$ gets its own subscript so we don't mix angles when we expand the product. $\theta_1$ belongs to $R_x$, $\theta_2$ to $R_y$, $\theta_3$ to $R_z$.

The three elementary rotations (symbolic)bnf
R_x(t1) = [ 1     0          0      ]
          [ 0   cos t1   -sin t1   ]
          [ 0   sin t1    cos t1   ]

R_y(t2) = [  cos t2   0   sin t2 ]
          [    0      1     0    ]
          [ -sin t2   0   cos t2 ]

R_z(t3) = [ cos t3  -sin t3   0 ]
          [ sin t3   cos t3   0 ]
          [   0        0      1 ]

§ 06

Hand multiplication — $R_y(\theta_2)\,R_x(\theta_1)$

Working slowly, row-of-the-first times column-of-the-second, we expand $R_y(\theta_2) \cdot R_x(\theta_1)$. Most cells collapse to zero because of all the zeros in the elementary matrices — the work is in tracking what survives.

The intermediate compound (after two rotations) comes out to:

$$R_y R_x \;=\; \begin{bmatrix} \cos\theta_2 & \sin\theta_1 \sin\theta_2 & \cos\theta_1 \sin\theta_2 \\ 0 & \cos\theta_1 & -\sin\theta_1 \\ -\sin\theta_2 & \sin\theta_1 \cos\theta_2 & \cos\theta_1 \cos\theta_2 \end{bmatrix}$$
Take it column by column — your brain will try to do it all at once, don't let it.
Sign discipline

The $-\sin\theta_2$ in the bottom-left and the $-\sin\theta_1$ in the middle-right are the most common places to drop a minus sign. Slow down there.

WidgetBuild the intermediate compound by hand: pick a row of $R_y$ and a column of $R_x$, compose the dot product term-by-term, and drop the result into the $3\times 3$ grid. The widget flags sign drops on the spot.

§ 07

Bringing in $R_z(\theta_3)$ — the full $R_c$

Now we pre-multiply the previous result by $R_z(\theta_3)$ and grind through nine more dot products. The final compound rotation matrix is:

$$R_c \;=\; \begin{bmatrix} c_2 c_3 & s_1 s_2 c_3 - c_1 s_3 & c_1 s_2 c_3 + s_1 s_3 \\ c_2 s_3 & s_1 s_2 s_3 + c_1 c_3 & c_1 s_2 s_3 - s_1 c_3 \\ -s_2 & s_1 c_2 & c_1 c_2 \end{bmatrix}$$

where $c_i = \cos\theta_i$, $s_i = \sin\theta_i$. This is the analytical proof we'll compare MATLAB against.

This lovely, beautiful compound matrix is what any sequence of three axis rotations boils down to.
Sanity checks

Set $\theta_2 = \theta_3 = 0$ → should reduce to $R_x(\theta_1)$. Set $\theta_1 = \theta_3 = 0$ → should reduce to $R_y(\theta_2)$. Try them on paper as a self-check.

§ 08

Example 7 — composing rotations in MATLAB

Instead of one giant loop, we chain three loops back-to-back: first sweep $\theta_1$ to $45°$ around $x$, then sweep $\theta_2$ to $220°$ around $y$ on top of that, then sweep $\theta_3$ to $300°$ around $z$ on top of that.

The trick is the running compound: at each stage we pre-multiply the previous compound by the new elementary rotation. Two variables keep us honest — RC1 after the second rotation, RC2 after the third.

What you should see

The fly sweeps an arc, then the whole arc swings around the next axis, then around the third. The mobile frame and the point move together at every step.

Three sequential rotations (Example 7, sketch)matlab
a_uvw = [0.3; 0.4; 0.5];
E     = eye(3);

% --- rotation 1: around x, theta1 in 0..45 -------------
for t1 = 0:0.5:45
    RX  = rota_x(t1);
    a   = RX * a_uvw;
    clf; hold on
    drawSyst(E); drawSyst(RX);
    plot3(a(1,1), a(2,1), a(3,1), '.', 'MarkerSize', 20);
    drawnow
end

% --- rotation 2: around y, theta2 in 0..220 ------------
for t2 = 0:0.5:220
    RC1 = rota_y(t2) * RX;        % pre-multiply
    a   = RC1 * a_uvw;
    clf; hold on
    drawSyst(E); drawSyst(RC1);
    plot3(a(1,1), a(2,1), a(3,1), '.', 'MarkerSize', 20);
    drawnow
end

% --- rotation 3: around z, theta3 in 0..300 ------------
for t3 = 0:0.5:300
    RC2 = rota_z(t3) * RC1;       % pre-multiply again
    a   = RC2 * a_uvw;
    clf; hold on
    drawSyst(E); drawSyst(RC2);
    plot3(a(1,1), a(2,1), a(3,1), '.', 'MarkerSize', 20);
    drawnow
end

WidgetStep through Example 7 stage by stage. Sweep $\theta_1$ to $45°$, then $\theta_2$ to $220°$ on top of that, then $\theta_3$ to $300°$. The running compound $R_{C1},\,R_{C2}$ updates after each stage and the fly's trail shows the whole journey.

§ 09

Example 8 — wrapping it as rotacomp(t1,t2,t3)

Why re-multiply at every step when we have the closed-form $R_c$? We write a single function rotacomp(t1,t2,t3) that returns the compound matrix in one shot.

Every angle that appears inside the function must be declared as an input — t1, t2, and t3. Forget one and MATLAB will complain it's undefined. Then in the animation loops we just call RC = rotacomp(t1,t2,t3) and everything else is identical to Example 7.

If your animation runs but looks wrong, ninety percent of the time you forgot to update all the RC references — not just the first one.
The gotcha

When refactoring, search-and-replace every occurrence: the matrix-build line, both drawSyst(...) calls, the a = RC * a_uvw line. Missing one leaves a stale matrix in the loop and the animation drifts.

The compound rotation as a functionmatlab
function RC = rotacomp(t1, t2, t3)
    RC = [ cosd(t2)*cosd(t3), ...
           sind(t1)*sind(t2)*cosd(t3) - cosd(t1)*sind(t3), ...
           cosd(t1)*sind(t2)*cosd(t3) + sind(t1)*sind(t3);

           cosd(t2)*sind(t3), ...
           sind(t1)*sind(t2)*sind(t3) + cosd(t1)*cosd(t3), ...
           cosd(t1)*sind(t2)*sind(t3) - sind(t1)*cosd(t3);

          -sind(t2), ...
           sind(t1)*cosd(t2), ...
           cosd(t1)*cosd(t2) ];
end
Using rotacomp inside the animationmatlab
t1 = 0; t2 = 0; t3 = 0;
for t1 = 0:0.5:45
    RC = rotacomp(t1, t2, t3);
    a  = RC * a_uvw;
    clf; hold on
    drawSyst(E); drawSyst(RC);
    plot3(a(1,1), a(2,1), a(3,1), '.', 'MarkerSize', 20);
    drawnow
end
% then loop t2 to 220, then t3 to 300 — same pattern
§ 10

Proving the two approaches agree

Run Example 7 (chained pre-multiplication) and Example 8 (rotacomp) with the same angle schedule. The fly should trace exactly the same path, and the printed matrix should be identical at every angle.

This is the empirical confirmation that the hand-derived $R_c$ is correct — and it's the kind of cross-check you should reach for any time you're unsure whether a closed-form expression matches the step-by-step construction.

Same result, two roads — that's how you know the maths and the code are both telling the truth.
Numerical check

For a quick spot check, pick $(\theta_1,\theta_2,\theta_3)=(30°,45°,60°)$ and compare rota_z(60)*rota_y(45)*rota_x(30) against rotacomp(30,45,60). They must agree to machine precision.
