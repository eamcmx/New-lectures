The Stored-Program Idea — the program moves into memory

June 1945: John von Neumann's "First Draft of a Report on the EDVAC" proposes something the six machines you just operated never had — put the program and the data in the same memory, both as plain numbers, read by a CPU (control unit + ALU + registers) over a shared bus. Below is that machine, small enough to see through. Press ▶ Run and watch instructions get fetched out of memory itself — then let the program rewrite its own code.

The problem you just lived

Zuse Z3 · 1941

Its program was holes in a strip of movie film, pulled through a reader outside the machine. No branch instruction existed at all — to loop, you glued the film into a ring.

Harvard Mark I · 1944

A paper tape fed instructions strictly one after another. Want a loop? Splice the tape into a physical loop. Want an if? Stop the machine and swap tapes.

↩ replay the Mark I →
ENIAC · 1945

Electronic and blazingly fast — but the program was the wiring. Changing it meant re-plugging hundreds of cables and dials: days of work to run a new problem for seconds.

↩ replay ENIAC →
In every machine so far, the program lives outside the machine's fast parts — on film, on tape, in the wiring. Data got electronic memory; instructions crawled in from the physical world. Von Neumann's fix: store the instructions where the data lives.

The instruction set (8 instructions) and its numeric encoding
LDA n1nnload memory cell n into ACC
ADD n2nnACC := ACC + memory[n]
SUB n3nnACC := ACC − memory[n]
STA n4nnstore ACC into memory cell n — even if that cell is an instruction
JMP n5nnset PC := n
JNZ n6nnif ACC ≠ 0, set PC := n — the conditional branch the Z3 and Mark I never had
OUT700print ACC to the output
HLT000stop. Note: HLT is the number 0 — the same 0 your data uses

An instruction is opcode × 100 + operand: ADD 12 is stored as the number 212. Nothing in a cell says whether it is code or data — only the PC decides, by pointing at it.

The showstopper · the program is just numbers

If instructions really are ordinary numbers in ordinary memory, then a program should be able to store into its own instructions — and the machine should obey the rewritten code without blinking. Let's prove it, one step at a time.

“No plugboard, no tape splice — the machine rewired itself in one instruction. This is what ENIAC's programmers got in EDVAC.”

The von Neumann bottleneck: one memory, one bus — so an instruction fetch and a data access can never happen at the same instant. Everything your CPU does queues on this wire. Watch a run: the blue fetch dots alone are roughly half the traffic. Modern machines fight this with caches, prefetchers and split L1 instruction/data caches (a little Harvard hiding inside every von Neumann chip) — but the bottleneck is baked into the architecture itself.

1936 closes its loop in 1945

Turing's universal machine was a mathematical trick: a machine that reads another machine's description off its own tape and becomes it. EDVAC is that trick in hardware — the “description” is the program in memory, and the control unit is the reader. Notice what you just did above: one physical machine became a summer, a multiplier, and a self-editor, without a single wire moving.

Software is born

On ENIAC, changing the program was an engineering job — days of cables. Here, loading a program is just I/O: write some numbers into memory. That flip is what makes software an artifact you can ship — copy it, sell it, send it down a wire, load it in milliseconds. Every app store is downstream of the moment the program became data.

The dark twin

If code is data, then data can become code. The same property that let our demo rewrite an ADD into a SUB lets a buffer overflow smuggle instructions in through an input field — and lets a JIT compiler write fresh machine code into memory and jump to it. Exploits and V8's speed are both children of von Neumann. Architecture is destiny, for good and ill.

Simplifications

  • Tiny ISA: 8 instructions and one accumulator, versus the real EDVAC's 44-bit words, ~3.5 kwords of mercury delay-line memory, and a richer order code. The fetch–decode–execute rhythm and the unified store are the honest part.
  • Decimal encoding for readability: we store ADD 12 as the decimal number 212 so you can read cells at a glance; EDVAC (and everything since) encodes instructions in binary.
  • 16 cells so the whole store fits on screen; real programs obviously need more, but the point — code and data in the same cells — is unchanged at any size.
  • Instant memory: real delay-line memory made the CPU wait for a word to circulate past a read head; our cells answer immediately. The bus-dot animation is a cartoon of timing, not a model of it.
  • 0 is both “zero” and HLT in our encoding — a deliberate ambiguity. Real machines have the same property with different numbers: point the PC at data and it will cheerfully try to execute it.
