Exercise 1Architecture or organization?

Classify each statement as architecture or organization, with a one-line justification: (a) the semantics of x86's MOV instruction · (b) Intel vs AMD implementing x86 with different pipelines · (c) the number of ISA-visible registers · (d) moving from a 7 nm to a 5 nm process · (e) adding a new SIMD instruction-set extension · (f) doubling L1 cache associativity (same ISA).

Try first — hint

Don't memorize six answers. Find the one question that decides all of them, then ask it six times.

  1. Step 1 — the test question

    Ask: "if this changed, would correct software have to change?" If yes, it's programmer-visible → architecture. If programs run unmodified (only faster, cooler, or cheaper), it's organization.

    WHY — this is the lecture's definition made operational: architecture = what the system does (the contract with software); organization = how it's physically built.

  2. Step 2 — (a) MOV semantics

    (a) → architecture. Change what MOV means and every compiled binary on Earth breaks.

    WHY — instruction semantics are the core of the ISA: the exact behavior software is written against.

  3. Step 3 — (b) Intel vs AMD pipelines

    (b) → organization. Both chips run the same x86 binaries; the pipelines differ underneath.

    WHY — one architecture, two implementations. This is the textbook example: same contract, different machinery.

  4. Step 4 — (c) ISA-visible register count

    (c) → architecture. Compilers allocate those registers by name; add or remove one and code generation changes.

    WHY — "ISA-visible" literally means the programmer can name it. Hidden physical rename registers, by contrast, would be organization.

  5. Step 5 — (d) 7 nm → 5 nm

    (d) → organization (implementation technology). No program can even detect the transistor size.

    WHY — process shrinks change cost, power, and clock headroom — exactly the things the lecture says organization optimizes.

  6. Step 6 — (e) new SIMD extension

    (e) → architecture. New instructions exist only if software is rewritten (or recompiled) to emit them.

    WHY — an extension changes the instruction set itself. Software must opt in — the definition of a programmer-visible change.

  7. Step 7 — (f) doubling L1 associativity

    (f) → organization. Loads and stores behave identically; hit rate just improves.

    WHY — caches are (mostly) transparent: correctness never depends on them, only speed. Same ISA ⇒ same architecture.

Final answer
(a) Arch · (b) Org · (c) Arch · (d) Org · (e) Arch · (f) Org — every call decided by one question: does software have to change?

Exercise 2Turing machine trace — binary increment

Run the binary-increment machine from the Turing machine page on input tape 1011 (head on the first cell, state q0). Rules: (q0,0)→(0,R,q0), (q0,1)→(1,R,q0), (q0,□)→(□,L,q1), (q1,1)→(0,L,q1), (q1,0)→(1,N,halt), (q1,□)→(1,N,halt). Show the tape and state after every rule firing.

Try first — hint

The machine is doing grade-school +1 in binary: find the rightmost digit, then carry leftward. Predict how many 1s will flip to 0 before you trace a single step.

  1. Step 0 — initial configuration

    State q0, head on cell 0:  1011  (1011₂ = 8+2+1 = 11)

    WHY — phase one (q0) has one job: walk right past every digit to find the number's low end, where +1 must begin.

  2. Step 1 — fire (q0,1)→(1,R,q0)

    q0  1011

    WHY — reading a 1 while scanning: leave it, keep moving right. Nothing is changed yet.

  3. Step 2 — fire (q0,0)→(0,R,q0)

    q0  1011

    WHY — same scan, different symbol, same decision: pass over it. The rule table covers every (state, symbol) pair it might meet.

  4. Step 3 — fire (q0,1)→(1,R,q0)

    q0  1011

    WHY — still hunting for the right edge. The machine can't "see" the whole tape — it only knows the cell under the head.

  5. Step 4 — fire (q0,1)→(1,R,q0)

    q0  1011□

    WHY — it stepped off the number onto blank tape. That blank is the only signal that the rightmost digit is behind it.

  6. Step 5 — fire (q0,□)→(□,L,q1)

    q1  1011□

    WHY — the state change IS the algorithm switching phases: q0 = "searching", q1 = "carrying". The head turns around onto the lowest digit.

  7. Step 6 — fire (q1,1)→(0,L,q1)

    q1  1010□  — tape is now 1010

    WHY — 1+1 = 10 in binary: write 0, carry the 1 left. Staying in q1 means "I am still holding a carry."

  8. Step 7 — fire (q1,1)→(0,L,q1)

    q1  1000□  — tape is now 1000

    WHY — the carry ripples: another 1 absorbs it and becomes 0, and the carry keeps traveling. Exactly the bead-cascade from the abacus page.

  9. Step 8 — fire (q1,0)→(1,N,halt)

    halt  1100□  — tape reads 1100

    WHY — a 0 can absorb the carry without creating a new one: write 1, done. Halting is a deliberate rule, not an accident — the machine decides it's finished.

Final answer
Final tape 1100 after 8 rule firings. Check: 1011₂ = 11, and 1100₂ = 8+4 = 12 = 11+1. ✓ Two states + six rules = a working +1 circuit.

Exercise 3Program the Z3 — z = (a+b)·(a−b)

Using only the real Z3 operations — Lu (keyboard→register), Pr Zn (memory→register), Ps Zn (R1→memory, R1 clears), Ls1 (R1:=R1+R2), Ls2 (R1:=R1−R2), Lm (R1:=R1×R2), Ld (display R1) — and memory words Z1–Z3, write an instruction tape that computes z = (a+b)·(a−b) for keyboard inputs a=7, b=3, then dry-run it. (Loads auto-route: they fill R1 if it's free, otherwise R2.)

Try first — hint

You need a and b twice each, but the keyboard gives them once and binary ops clear R2. Where must they live between uses? That's what Z1–Z3 are for.

  1. Step 1 — plan before punching film

    Three sub-results: s = a+b, d = a−b, then z = s·d. Plan: park a→Z1 and b→Z2 immediately; compute the sum and park it in Z3; compute the difference; multiply by Z3; display.

    WHY — the Z3 has no branch and only two working registers, so a program is pure dataflow choreography: every value must be in the right place before the op that eats it.

  2. Step 2 — punch the tape (14 frames)
    #instreffect#instreffect
    1Lukeyboard a → R18Ps Z3sum → Z3
    2Ps Z1a → Z19Pr Z1a → R1
    3Lukeyboard b → R110Pr Z2b → R2
    4Ps Z2b → Z211Ls2R1 := a − b
    5Pr Z1a → R112Pr Z3sum → R2
    6Pr Z2b → R213LmR1 := R1 × R2
    7Ls1R1 := a + b14Ldlamps ← R1

    WHY — keyboard queue is 7, 3. Frames 1–4 secure the inputs in memory first, because Ls1/Ls2/Lm destroy R2 and Ps drains R1 — nothing survives in registers.

  3. Step 3 — trace frames 1–4: capture the inputs
    afterR1R2Z1Z2Z3
    1 Lu7————
    2 Ps Z1——7——
    3 Lu3—7——
    4 Ps Z2——73—

    WHY — after frame 2, R1 is empty again (Ps clears it), so the second Lu auto-routes into R1, not R2. The hardware's routing rule dictates instruction order.

  4. Step 4 — trace frames 5–8: the sum, parked
    afterR1R2Z1Z2Z3
    5 Pr Z17—73—
    6 Pr Z27373—
    7 Ls110—73—

    WHY — 7+3 = 10 lands in R1 and R2 clears; but Lm isn't ready to run yet (no second factor exists), so the sum must wait in Z3 while we build a−b.

  5. Step 5 — trace frames 9–11: the difference
    afterR1R2Z1Z2Z3
    9 Pr Z17—7310
    10 Pr Z2737310
    11 Ls24—7310

    WHY — operand order matters for subtraction: Ls2 computes R1−R2, so a must be loaded first (it takes R1). Load them the other way round and you'd get −4.

  6. Step 6 — trace frames 12–14: multiply and display
    afterR1R2Z1Z2Z3lamps
    12 Pr Z34107310—
    13 Lm40—7310—
    14 Ld40—731040

    WHY — with 4 sitting in R1, Pr Z3 auto-routes the parked sum into R2; Lm multiplies 4×10 = 40; Ld stamps it onto the lamp display. Fetch–execute–advance, frame after frame — a 1941 relay machine running the same rhythm as your CPU.

  7. Step 7 — verify

    (7+3)·(7−3) = 10·4 = 40. And 7²−3² = 49−9 = 40 — the program is a hardware proof of the identity (a+b)(a−b) = a²−b².

    WHY — always check a trace against math you trust. If the table said anything but 40, the bug would be in the choreography, not the arithmetic units.

Final answer
Tape: Lu · Ps Z1 · Lu · Ps Z2 · Pr Z1 · Pr Z2 · Ls1 · Ps Z3 · Pr Z1 · Pr Z2 · Ls2 · Pr Z3 · Lm · Ld with keyboard queue 7, 3 → lamps show z = 40. ✓ Paste it into the Z3 simulator and watch the relays agree.

Exercise 4Mark I difference table — f(x) = x² + 3x + 1

Using only additions (the method of finite differences, as on the Harvard Mark I), produce the table of f(x) = x²+3x+1 for x = 0…6. Set up the accumulators, give the loop, run it, and verify two values by direct computation.

Try first — hint

Compute f(0), f(1), f(2), f(3) by hand and subtract neighbors twice. What do you notice about the second row of differences?

  1. Step 1 — the seed value

    f(0) = 0² + 3·0 + 1 = 1. That's the only value of f we'll ever compute directly.

    WHY — the whole trick of a difference engine is to pay for one real evaluation up front, then coast on additions forever after.

  2. Step 2 — find the difference pattern

    Δ(x) = f(x+1) − f(x) = (2x+4). So Δ starts at 4 and grows by 2 each step: 4, 6, 8, 10, 12, 14. The second difference Δ² = 2, constant.

    WHY — the second difference of any quadratic is constant (here 2 = 2·1, twice the leading coefficient). Constant means "no more subtraction needed" — and that is the entire reason difference engines worked.

  3. Step 3 — load the accumulators

    A1 ← 1 (current f) · A2 ← 4 (current Δ) · C1 ← 2 (the constant Δ²).

    WHY — three storage counters hold the entire mathematical state: the value, its rate of change, and the rate of change of the rate of change. Nothing else about the polynomial needs to exist in the machine.

  4. Step 4 — the loop (three tape lines)

    TYPE A1 (print) → A1 += A2 (value climbs by Δ) → A2 += C1 (Δ climbs by 2) → repeat.

    WHY — squaring has vanished: two additions per table entry. The Mark I's 24-channel paper tape just repeated these lines; Babbage's engine did the same cascade in gears, a century earlier and unbuilt.

  5. Step 5 — run it, seven passes
    passTYPE printsA1 after +A2A2 after +C1
    111+4 = 54+2 = 6
    255+6 = 116+2 = 8
    31111+8 = 198+2 = 10
    41919+10 = 2910+2 = 12
    52929+12 = 4112+2 = 14
    64141+14 = 5514+2 = 16
    755(stop)—

    WHY — watch A2 tick 4, 6, 8, 10, 12, 14: the machine is integrating the constant 2 twice. Twelve additions produced a seven-entry quadratic table.

  6. Step 6 — verify two entries directly

    f(4) = 16 + 12 + 1 = 29 ✓  ·  f(6) = 36 + 18 + 1 = 55 ✓ — both match the printed column.

    WHY — spot-checking the middle and the end catches both a wrong seed and a drifting increment. Navy table-checkers did exactly this on "Bessie's" output.

Final answer
Printed column: 1, 5, 11, 19, 29, 41, 55 — a full quadratic table from additions alone, because Δ² of a quadratic is the constant 2.

Exercise 5Moore's Law arithmetic — and the wall it hit

(i) Intel's 4004 (1971) had 2,300 transistors. If counts double every 2 years, derive the predicted transistor count for 2023 and compare with Apple's M2 Ultra (1.34 × 10¹¹ transistors, 2023). (ii) If clock speeds had kept doubling every 2 years from 3 GHz in 2004, what clock would 2024 require? Why didn't it happen, and what did the industry do instead?

Try first — hint

Both parts are the same one-liner: count the doublings n, then multiply by 2n. The interesting part is which prediction came true.

  1. Step 1 — (i) count the doublings

    2023 − 1971 = 52 years. At one doubling per 2 years: 52 ÷ 2 = 26 doublings.

    WHY — exponential claims become checkable the moment you convert "keeps doubling" into an integer exponent. Everything else is multiplication.

  2. Step 2 — evaluate 2²⁶

    2¹⁰ = 1,024 → 2²⁰ = 1,048,576 → 2²⁶ = 2⁶ · 2²⁰ = 64 × 1,048,576 = 67,108,864.

    WHY — memorizing 2¹⁰ ≈ 10³ lets you size any power of two in your head: 2²⁶ ≈ 64 × 10⁶ ≈ 6.7 × 10⁷. The exact value confirms the estimate.

  3. Step 3 — the prediction

    2,300 × 67,108,864 = 23 × 67,108,864 × 100 = 1,543,503,872 × 100 = 154,350,387,200 ≈ 1.54 × 10¹¹ transistors.

    WHY — the 1965 back-of-envelope predicts ~154 billion transistors from a starting point of 2,300. No physical law forced this; it became a self-fulfilling industry roadmap.

  4. Step 4 — compare with reality

    M2 Ultra: 1.34 × 10¹¹. Ratio: 1.34 ÷ 1.5435 ≈ 0.87 — reality is only ~13% below the naive extrapolation, comfortably within 15% after 52 years and 26 doublings.

    WHY — an extrapolation across a factor of ~67 million landing within 15% is astonishing; almost no other engineering trend has ever held that long. That's why "Moore's Law" earned the name "law".

  5. Step 5 — (ii) the clock counterfactual

    2024 − 2004 = 20 years → 10 doublings. 2¹⁰ × 3 GHz = 1,024 × 3 GHz = 3,072 GHz ≈ 3 THz.

    WHY — the same arithmetic that worked for transistors demands a three-terahertz CPU. Real 2024 desktop clocks: still ~3–6 GHz. Two identical extrapolations, one triumph, one flatline.

  6. Step 6 — why the wall, and the industry's answer

    Dynamic power scales roughly with frequency × voltage² — pushing toward THz would concentrate more heat per mm² than we can remove; the chip would destroy itself. So around 2004 clocks plateaued and the industry pivoted: more cores, not faster cores — multicore CPUs, GPUs, clusters, accelerators.

    WHY — transistor count kept doubling (they got smaller), so the budget was spent sideways on parallelism. This single fork explains why modern performance belongs to whoever writes parallel software.

Final answer
(i) Predicted 2,300 × 2²⁶ = 154,350,387,200 ≈ 1.54 × 10¹¹; M2 Ultra's 1.34 × 10¹¹ is within ~15% — the transistor prediction held for 52 years. (ii) Clocks would need 2¹⁰ × 3 GHz ≈ 3 THz — impossible (power/heat wall), so the industry went multicore instead.
